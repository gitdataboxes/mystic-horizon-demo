# AGENTS.md — Mystic-Horizon

## Project Overview

Local CLI phone agent in Python. It answers calls, remembers conversations, identifies commitments, and acts autonomously. It can run with Twilio + LiveKit for phone calls and with dashboard/CLI channels for owner text and voice interaction.

## Architecture

```text
Twilio Call -> Webhook -> LiveKit Room -> Agent Pipeline -> Extraction -> Actions -> Scheduler
Dashboard  -> aiohttp    -> Owner Chat / Settings / Knowledge Graph / htmx navigation (SSE)
Dashboard  -> LiveKit SDK -> LiveKit Room (direct browser connection for voice/text)
Dashboard  -> aiohttp    -> Relationship Graph API (agent hub + people + channel-strand edges; drill-in via thread endpoint)
CLI        -> Unix Socket -> Daemon (start/stop/health)
CLI        -> DB Direct   -> Resource queries (people, calls, actions, facts, ...)
```

The closed loop is unchanged: calls create knowledge, knowledge creates commitments, commitments create future calls. The dashboard and CLI provide two additional surfaces for the owner to interact with agent state.

## Stack

| Layer | Python (`mystic/`) |

| Logging | `structlog` |

## Conventions

- IDs: `uuid.uuid4()`
- Timestamps: Unix epoch ms via `int(time.time() * 1000)`
- CLI requires `--agent <name>` or `MH_AGENT`
- Agent data is isolated at `~/.mystic-horizon/{agent-name}/`
- Shared binaries live at `~/.mystic-horizon/bin/`
- Use `.venv/bin/python` for repo-local commands and tests
- Skills return natural language strings for the voice agent to speak
- Source tracking is derived from execution context, never from model output

## Commands

```bash

.venv/bin/mystic-horizon setup                               # one-shot: auto-config, start daemon, open dashboard
.venv/bin/mystic-horizon --agent <name> init                 # quick init (TTS + STT provider choice)
```

## Key Patterns

- Hybrid retrieval combines vector search with FTS5 and supports SQL-level person scoping. Source row loading is batched (`WHERE rowid IN (...)`) for efficiency.
- Per-call extraction runs in two phases: parallel transcript/summary/fact/commitment work, then sequential person-summary and satisfaction work. Nightly extraction consolidates a day's interactions per person into `day_summaries` — merges transcripts, extracts summary/facts/commitments at the day level, rebuilds person summaries from day summaries. A nightly loop runs at 2 AM agent-local time; on startup, missed days are caught up automatically.
- Interaction vocabulary: every interaction (call, chat, CLI session) carries `direction` (inbound/outbound), `channel` (phone/dashboard/sms/cli), and `modality` (voice/text/mixed). `interactions.py` normalizes and labels these into `InteractionDescriptor` with human-readable labels (e.g., "Outbound phone call", "Dashboard chat"). All event payloads, prompt variables, graph nodes, and CLI serialization include interaction metadata.
- Active calls are stored in SQLite and mirrored in memory for resilience across restarts.
- Scheduler ticks every 60 seconds: syncs calendar feeds, fires reminders, retries pending hub calendar syncs, then filters out `in_progress` or exhausted actions. `get_due_actions` considers `COALESCE(due_at, start_at)` for scheduling. The `notify` decision sends a desktop notification and reschedules without incrementing attempts.
- Webhooks validate `X-Twilio-Signature`; media stream URLs use HMAC-SHA256 auth.
- Runtime startup flows through `Runtime` with three entry points: `start_full` (daemon mode — owns DB, full stack), `start_dev` (foreground — DB + optional LiveKit + server, no Twilio/worker/scheduler), and `start_runtime_from_setup` (setup flow — reuses existing DB, supports progress callbacks and `before_server` hook for port handoff). All delegate to `_start_runtime(db, owns_db, on_progress, before_server)`. Twilio-enabled startup binds localhost first, starts the HTTP server, then runs `ensure_phone_line_ready(repair=True)` and launches the phone reconcile loop. Shutdown drains sweep, phone reconcile, nightly extraction, and bridge tasks.
- `start` spawns a daemon process (`_serve` hidden command) with stderr redirected to `APP_HOME/logs/mystic-horizon.log`. The caller polls `probe_daemon()` until healthy, then returns JSON status. On startup failure, the error includes recent log output via `_tail_log()`. `stop` sends a shutdown command via socket. `health` probes daemon health, checks subsystems (db, stt, tts, turn_detection, livekit, twilio, smtp, tailscale, funnel, phone), gathers DB stats, and includes a top-level `phone` block from `ensure_phone_line_ready(repair=False)`. Turn detection reports `ok` (package + assets present or remote inference), `degraded` (missing package or assets), or `not_configured` (voice pipeline not configured). `start_server` from `mystic.server` is also used by the setup flow to run a temporary web server during onboarding.
- `setup` is a one-shot command: generates default config (no voice providers pre-selected), downloads the LiveKit binary, seeds dashboard defaults, starts a temporary setup web server (`create_setup_app`) that serves the onboarding wizard. The prepare flow downloads dependencies only (no in-process runtime) with granular progress via `on_detail` callback. After completion, the setup server is closed to free the port, then a background daemon is spawned. The browser polls `/health` until the daemon is reachable, then redirects to `/dashboard/page/home`. If a daemon is already running, setup reuses it and skips the temporary server. `_open_browser` uses `xdg-open`/`open` subprocess instead of `webbrowser.open`. The dashboard setup page is a full onboarding wizard — cloud/local toggle for LLM/STT/TTS, inline API key validation (imports missing keys from sibling agents), model selection, and step-by-step dependency preparation with SSE progress (`prepare.step` for major stages, `prepare.detail` for granular progress; steps: voice server, STT, TTS, embedding, launch). Each step has an expandable terminal showing live detail lines. Setup writes to `providers.json`, `agent.json`, and `intelligence.json` (propagates the selected LLM model to all backend task slots). Dashboard pages redirect to `/dashboard/setup` when LLM provider is unconfigured or STT/TTS providers are not ready (in dev mode, shows inline warning banners via `_with_dashboard_warnings` instead). "Setup" is not in the main nav — it's a gatekeeper page. Settings link in gear menu dropdown. The setup page uses a dedicated minimal shell (`setup-shell.html`) without sidebar or navigation. No dedicated `/dashboard/live` route — HUD, chat, and voice controls are part of the shell and persist across all pages. Default landing page is `/dashboard/page/home` (knowledge graph).
- Preflight check validates runtime dependencies (livekit-server, Tailscale, Moonshine Voice package, Deepgram plugin when using Deepgram STT, LiveKit turn detector package and model assets when voice pipeline is configured, embedding model files, Pocket ONNX models when using Pocket TTS). Turn detector asset checks verify the concrete HuggingFace tokenizer/model files via `hf_hub_download(local_files_only=True)` instead of importing `AutoTokenizer`. Turn detector checks are skipped when using remote EOT inference (`LIVEKIT_REMOTE_EOT_URL`). Preflight is advisory — `run_serve` logs warnings but starts the server anyway so the dashboard is reachable for configuration. Unconfigured voice providers skip local model checks.
- Tailscale Funnel is the tunnel provider when Twilio is configured. `start_tunnel(port)` first reuses an already-matching Funnel when possible, otherwise runs `tailscale funnel --bg --yes --https=443 <port>` with a bounded timeout and returns the stable `https://<hostname>.ts.net` URL. `check_tailscale_ready()` validates install and auth, `get_tailscale_funnel_status()` exposes current Funnel status text, and `tailscale_funnel_matches_port()` best-effort matches Funnel output to the app port. `ensure_phone_line_ready()` in `phone.py` is the source of truth for whether Tailscale, Funnel, and Twilio webhooks are ready. `stop_tunnel()` runs `tailscale funnel off`. `AgentTunnelConfig` has a single `enabled: bool` field — no named/ephemeral modes.
- `init` defaults to quick mode (TTS provider choice + STT provider choice, minimal prompts); `--advanced` enables full owner/LLM configuration. Owner phone is optional and deferred to `--connect-twilio`. Init does not run the bootstrap conversation — it creates a pending bootstrap action. The dashboard live page detects missing identity/soul and automatically starts the bootstrap conversation. Init does not write IDENTITY.md/SOUL.md — bootstrap happens through the normal conversation flow.
- Embedding config is `LocalEmbeddingConfig` stored under `providers.json` key `"embedding"`. Default is `local` (nomic-embed-text-v1.5, 256-dim). `embed_chunks`/`embed_query` live in `mystic.embedding` and are re-exported from `mystic.memory`. Models must be pre-downloaded via `init`; inference raises if files are missing.
- Vec table dimensions are parameterized. On schema init, if the stored dimension mismatches the configured dimension, the vec tables are dropped and recreated and all embedding blobs are nullified for re-processing by the retry loop.
- Local embedding models are stored at `~/.mystic-horizon/models/` (shared across agents, like binaries). Downloaded once during `init` with atomic writes (temp file + rename).
- TTS supports two providers: Pocket TTS ONNX (local, vendored under `vendor/`, model weights at `~/.mystic-horizon/models/pocket-tts-onnx/`) and Inworld TTS (cloud, via `livekit-plugins-inworld`). Voice prompts are `.wav` clips in `voices/`; setup defaults new agents to Olivia while the game Copilot explicitly uses Hades. `TtsConfig = PocketTtsConfig | InworldTtsConfig | UnconfiguredTtsConfig`. Inworld allows >1 concurrent active jobs (cloud-based, not CPU-bound). `create_tts` dispatches to the correct adapter based on config type; raises `RuntimeError` when unconfigured.
- STT supports two providers: Moonshine Voice (local, native FFI streaming transcriber) and Deepgram (cloud, via `livekit-plugins-deepgram`, default model `nova-3`). `SttConfig = MoonshineSttConfig | DeepgramSttConfig | UnconfiguredSttConfig`. `create_stt` dispatches on config type; raises `RuntimeError` when unconfigured. Deepgram plugin is lazy-imported.
- Preflight checks validate that Pocket ONNX model files are present and that `tts.model` is "default" or empty. Inworld plugin is installed during `ensure_dependencies` when selected. Unconfigured providers are silently skipped.
- LiveKit dependency handling is centralized in `mystic.livekit`: system PATH is preferred, macOS installs via Homebrew and symlinks the managed path, Linux downloads a checksummed tarball, and shared missing-binary guidance is platform-specific. `start_livekit_server` passes explicit `--rtc.tcp_port` (port+1) and `--udp-port` (port+2) flags to bind RTC ports deterministically. Output capture merges stdout+stderr (`stderr=subprocess.STDOUT`) into a single tail buffer.
- Shared timestamp helpers (`now_ms`, `parse_due_at`, `format_due_at`) live in `mystic.db` — no per-module copies.
- Journal system: `write_soul()` and `write_identity()` save the previous version to `APP_HOME/journal/{soul|identity}/{timestamp}.md` before overwriting. Each journal entry has frontmatter (timestamp, trigger, note) and the full prior content. `recall-self` skill lists recent entries or reads a specific snapshot by timestamp. Replaces the old `.bak` single-backup approach.
- Owner phone is optional throughout: `AgentOwnerConfig.phone` can be `None`. Guard clauses in `calls.py`, `actions.py`, and `cli.py` allow fully local operation.
- Tool schemas and `execute_tool` live in `skills.py` and are transport-agnostic. Each skill now exposes its own tool schema via `build_skill_tool_schema(skill)`, with name, description (including `## Gotchas` if present), modality filter (`voice`, `text`, or both), and per-skill parameters (required/optional with descriptions) sourced from SKILL.md frontmatter. `build_tools_for_context(registry, audience, modality)` filters by invoke permissions and modality. Skills removed the old `read/write/edit` multiplexed tool pattern and `TOOL_SKILL_MAP` — tools are now named directly (e.g., `read-facts`, `write-action`, `edit-soul`). `SkillMetadata` carries `modality`, `parameters` (`SkillParameters`), and `gotchas` fields. `voice.py` wraps skill schemas as LiveKit function tools via `_make_skill_voice_tool` (raw-arguments pattern with tool event timing). `llm.py` can use the direct schemas via `stream_llm_with_tools`. `audio_source` is threaded through the skill execution pipeline for skills that inject audio into live calls.
- Call control uses two Twilio REST primitives: `update_live_call()` mutates a live call's TwiML/URL, `generate_dial_twiml()` builds `<Dial>` verbs with action URLs. `reconnect_call_to_stream()` rebuilds stream TwiML after transfer failure or hold resume. Transfer target SIDs are tracked in-memory and cleaned up on call end. The `/webhook/twilio/dial-action` endpoint handles Dial verb completion.
- `on_send_text` callback (wired in `worker.py`) publishes `agent_chat_response` events and records transcript entries — used by the `chat` voice tool and `send_text` tool to deliver text messages to the browser.
- Trace ID (`bind_trace_id`) is a `ContextVar` set per call/session; auto-injected into structlog entries and LLM `X-Request-Id` headers.
- `chat` is a scriptable text chat command (`--message` for single-shot, stdin for multi-line) — returns JSON responses. Voice conversations happen via the dashboard live page.
- `start` auto-kills stale daemon processes before cleanup (`SIGTERM` with 2s wait). `start_livekit_server` auto-kills orphaned livekit-server processes (`SIGKILL` with 2s wait) instead of failing on port conflict.
- Agent wall-clock awareness: `voice.MysticAgent` is the default `agent_cls` for the LiveKit pipeline. Before every user turn, `on_user_turn_completed` purges stale `mh-time-*` system messages and inserts a fresh timezone-aware `Current time:` stamp (agent config timezone, with a sensible UTC fallback) with a stable id prefix so only one stamp is ever present. This replaces baking the current time into the static system prompt — the LLM always sees the actual wall-clock time at reply generation.
- Search LLM routing: `llm.py` hardcodes `task == "search"` (i.e., `read-search`) to OpenRouter `perplexity/sonar-pro` via `_get_openrouter_search_backend()`. The configured realtime/backend LLM is bypassed for search — even a custom local backend still sees search queries hit OpenRouter directly. Raises `ValueError` if the OpenRouter API key is missing. Search requests still carry OpenRouter referrer/title headers.
- Agent transcript events: `worker.py` publishes `user_input_transcribed`, `user_chat_received` (with `clientMessageId` when present), `agent_voice_transcribed` (voice mode, with `transcript` and `is_final`), `agent_chat_response` (text mode), `tool_started`, `tool_completed`, and `agent_error` events to a `lk.agent.events` LiveKit data channel topic via `local_participant.publish_data()`. Agent speech always publishes an event to the data channel regardless of audio state — `agent_voice_transcribed` when audio is enabled, `agent_chat_response` when disabled. Agent speech is also delivered to the browser via native LiveKit transcription text streaming (`lk.transcription` handler registered by the browser). The browser connects directly to the LiveKit room via the LiveKit client SDK (`livekit-client.umd.js`) and receives agent speech via `room.registerTextStreamHandler("lk.transcription", ...)` with streaming segment updates (progressive text accumulation per `segmentId`); the `agent_voice_transcribed` data channel event provides a HUD-level mirror of agent voice output. Browser maintains a 60s heartbeat (`mh.ping` data channel, `reliable: true`) to keep the server-side idle timer from expiring. Text and voice input share a unified pipeline — text input calls `session.interrupt()` then `session.generate_reply(user_input=text)`. No `last_input_modality` tracking — agent speech routing is handled by the LiveKit SDK's native transcription streaming. Text input accepted via both `room_io.TextInputOptions` and `mh.chat` data channel (data channel messages include `clientMessageId` for deduplication). Text deduplication uses `clientMessageId` (preferred) or stream ID as the dedupe key via `seen_text_stream_ids` set. `_safe_process_text_input` wraps text input handling with error recovery — catches exceptions and publishes `agent_error` events. Chat transcript entries persisted to a call record via `_append_chat_entry` (timestamped `[M:SS] Label [text]: content` format); agent speech also persisted. Idle session timeout (120s, reset by any data channel activity including heartbeat pings) auto-closes inactive sessions. Pipeline creation failures publish `agent_error` events. Bootstrap sessions (`metadata.bootstrap=True` with no `firstMessage`) call `session.generate_reply()` instead of speaking a hardcoded first message. Turn detection uses the multilingual plugin when available (with graceful init failure fallback), VAD interruption mode. Per-item metrics (transcription_delay, end_of_turn_delay, llm_ttft, tts_ttfb, e2e_latency) logged from `ConversationItemAddedEvent.item.metrics`. Voice control: `mh.voice_control` data channel accepts `{"action": "start"|"stop"}` packets with participant identity extraction — dashboard inbound owner sessions start text-first with audio disabled on both session input and output; browser sends start/stop packets when mic is enabled/disabled; on start, `room_io.set_participant(participant_identity)` rebinds the session's audio source, then audio is cycled off→on to re-subscribe to tracks from the current participant (handles browser page refresh reconnection); `_set_session_audio_enabled` toggles LiveKit session I/O (handles both sync and async `set_audio_enabled` methods). Dashboard owner sessions set `close_on_disconnect = False` on `RoomOptions` so the agent worker survives browser disconnects/refreshes without closing. Agent speech modality tracked via `voice_audio_enabled` flag — when disabled, agent speech records `modality="text"`, publishes `agent_chat_response` events, and appends to chat feed instead of voice delivery. Non-dashboard calls (public audience, outbound direction) keep audio enabled.
- Call recording is opt-in via `agent.json` `"recording": {"enabled": true}`. `CallRecorder` (in `audio.py`) writes stereo 16kHz PCM16 WAV files — caller on left channel, agent on right. `start_call_recorder()` returns `None` when disabled. Twilio `AudioBridge` accepts an optional `recorder` parameter. Recordings are stored at `APP_HOME/recordings/{call_id}.wav`.
- Bootstrap prompt (`bootstrap.md`) is modality-agnostic (works from both voice calls and dashboard text chat). Leads with speaking style (casual, short turns, one question at a time), instructs agent not to narrate its own state ("just woke up"), then guides identity discovery (name, nature, vibe, emoji → `write-identity`), soul conversation (values, boundaries → `write-soul`), and optional phone setup mention (directs to Settings page — no in-conversation credential collection). `bootstrap-v2.md` preserves the prior verbose version but with the same simplified connect phase (Settings page direction).
- `SetupStatus` (in `config.py`) checks identity, soul, Tailscale, and Twilio readiness. `core_complete` requires identity + soul. Used by init summary and `start` warning.
- DB migrations are ordered and numbered (9 built-in). `write_builtin_migrations()` generates built-in migrations (001: initial schema, 002: `answered_at`, 003: `last_extraction_attempt_at`, 004: calendar phase 1 — `actions.start_at`/`end_at` columns + `external_events` table, 005: calendar phase 2 — `actions.hub_event_id`/`hub_sync_status`/`hub_sync_attempts` columns, 006: `day_summaries` table — per-person per-date consolidated summaries with extraction tracking, 007: `channel` and `modality` on calls and active calls, 008: `calls.is_game_mode` + `game_scores` leaderboard table, 009: drops `calls.is_game_mode` now that game sessions live in their own ephemeral LiveKit room and are not persisted as calls — `game_scores` is retained for the Asteroids leaderboard). `create_migration` CLI command creates user-defined migrations (next number is 010). `run_migrations()` applies pending migrations in order. Drift detection skips migrations when schema was manually altered (`_calendar_phase_1_ready` for 004, `_calendar_phase_2_ready` for 005, `_day_summaries_ready` for 006, `_channel_ready` for 007, `_game_scores_ready` for 008, `_is_game_mode_dropped` for 009).
- `voice.py` re-exports audio and worker APIs for backward compatibility — new code should import directly from `mystic.audio` and `mystic.worker`.
- Calendar support (`calendar.py`) syncs ICS feeds via `maybe_sync()` with configurable interval, stores events in `external_events` table, and prunes stale entries. `check_availability()` and `find_open_slots()` merge external events with scheduled actions. `check_reminders()` sends desktop notifications for upcoming events/actions. ICS parsing uses optional `icalendar` + `recurring-ical-events` (lazy import). `format_current_schedule()` and `format_upcoming_schedule()` produce prompt context injected via `compute_variables()` — audience-scoped (owners see all, public sees own appointments). Scheduler integration: `maybe_sync`, `check_reminders`, and `maybe_retry_hub_sync` run at the top of each scheduler tick. `init --connect-calendar` provides an interactive wizard for adding ICS URLs. `init --connect-hub-calendar` provides a wizard for connecting a hub calendar (Google/Outlook/CalDAV) for event write-back with OAuth2 PKCE flow. Calendar config (`CalendarConfig` with `subscriptions`, `sync_interval_minutes`, `reminder_minutes`, `hub`) lives in `providers.json`. Hub OAuth tokens stored separately at `APP_HOME/config/hub_tokens.json` (atomic writes, hourly refresh for Google/Microsoft, basic auth for CalDAV). 4 calendar skills: `read-calendar` (audience-scoped upcoming items), `check-availability` (free/busy with owner conflict details), `find-open-slots` (merged availability windows), `manage-appointment` (cancel/reschedule with SMS confirmation and hub calendar sync).
- Dashboard surface is served by `web.py` under `/dashboard/*`. Auth via `mh_session` cookie (HMAC-SHA256 of the dashboard token). Login accepts a `token` query param and sets the session cookie. Dashboard pages are owner-editable HTML files stored at `APP_HOME/dashboard/`. History is preserved — each overwrite saves the prior version to `dashboard/.history/{timestamp}-{name}` with YAML frontmatter. Skills: `read-dashboard` lists/reads files, `design-dashboard` (cognitive, text-only modality, LLM task `editing`) generates revised HTML/CSS. `seed_dashboard_defaults()` copies default pages from `_assets/dashboard/defaults/`. SSE via `/dashboard/stream` pushes live events to connected clients; `_write_sse` helper handles disconnect/runtime errors gracefully and shutdown wakes stream queues so they exit cleanly. Settings page includes voice provider selection (STT/TTS dropdowns), readiness status badges, and a "Prepare" button (`POST /dashboard/f/prepare`) that triggers background dependency downloads via `ensure_dependencies` (quiet mode). Prepare progress broadcasts via SSE (`prepare.started`/`prepare.step`/`prepare.detail`/`prepare.done`/`prepare.error`). All text chat goes through the LiveKit data channel — server-side chat endpoints have been removed. Chat transcript persistence handled by `worker.py` via `_append_chat_entry`. Dashboard live voice uses the LiveKit client SDK in the browser — `POST /dashboard/api/voice/token` returns room credentials (token, URL using request host, room name, call ID, participant name, chat history, and separate live-call `hudHistory`), `/dashboard/api/voice/history` can rehydrate those split histories after page load, and the browser connects directly to the LiveKit room. Agent speech received via native LiveKit transcription text streaming (`room.registerTextStreamHandler("lk.transcription", ...)`) with progressive segment-based updates (streaming messages tracked by `segmentId`, finalized when `streaming: false`); `agent_voice_transcribed` data channel events also mirrored to HUD. Browser sends a 60s heartbeat (`mh.ping` data channel, `reliable: true`) to keep the server-side idle timer from expiring. Voice session metadata includes `chatCallId` for chat transcript persistence. Browser auto-connects to the voice bridge on page load. `sendChat()` includes a `clientMessageId` (UUID) for deduplication and waits for `user_chat_received` echo confirmation (5s timeout); ACK resolution uses `clientMessageId` instead of message text matching — only appends the user message if ACK was not already resolved (prevents duplicates). `agent_error` events reject pending chat acks and surface errors. `tool_started`/`tool_completed` events render as inline tool activity cards; multiple active cards are tracked by tool name so overlapping tools complete the matching card. Agent messages render with client-side markdown (bold, italic, links, code, lists, tables, blockquotes, headers). Tool card args summary uses `escapeHtml` for XSS safety. Typing indicator during agent processing (scrolls feed on show). Audio tracks auto-attach/detach via `TrackSubscribed`/`TrackUnsubscribed` handlers. Voice disconnect cleanup (`postVoiceDisconnect`) sends `participantName` in the disconnect request and uses a `disconnectNotified` flag to prevent duplicate calls; called on both manual disconnect and unexpected disconnection/connection errors. Dev mode (`app["dev_mode"]`) shows inline warning banners via `_with_dashboard_warnings` on dashboard pages instead of redirecting to setup when providers are missing. Relationship knowledge graph API (see `GRAPH.md` for the design manifesto): `GET /dashboard/api/graph?n=…&window=…` returns an `agent` hub node plus person nodes only (no fact/call/action nodes) with stable chronological `angleIndex`/`angle`/`radius` slots and one strand edge per `(person, channel, modality)` combination — edge `weight`/`recency`/`total`/`recentCount`/`inboundCount`/`outboundCount` drive visual encoding; `meta` carries `visibleLimit`/`activityWindowDays`/`hiddenPeople`/`totalPeople`. `GET /dashboard/api/graph/node/agent/agent` returns agent identity (`name`/`creature`/`vibe`) + `identityReady`/`soulReady`/`journalDepth` + person/call counts. `GET /dashboard/api/graph/node/person/{id}` adds `factCount`/`pendingActionCount`/`identified` plus per-channel `strands` for drill-in. `GET /dashboard/api/graph/thread/{person_id}/{channel}[/{modality}]` returns interaction history for a single strand with `transcriptPreview`. `POST /dashboard/api/graph/person/{id}/name` resolves unnamed callers inline and broadcasts a `person_renamed` activity event. Facts, call transcripts, and pending actions are content (surfaced in node detail + search), not graph citizens. htmx partial rendering: `render_shell` returns content-only for `HX-Request` headers, full shell for direct navigation. No dedicated `/dashboard/live` route — HUD, chat, and voice controls are part of the shell and persist across all pages. Default landing page is `/dashboard/page/home`. Three-column layout: collapsible left nav sidebar, main content, collapsible resizable right chat sidebar with tabs (chat + search). Icon-based SVG navigation with home excluded from nav (accessed via brand logo). `POST /dashboard/api/voice/disconnect` accepts optional `participantName` for identity-based release. Voice session lifecycle: `DashboardVoiceSession` tracks participants by name via `participant_names` set (identity-based acquire/release — named participants prevent duplicate disconnects, unnamed legacy releases are ignored when named participants exist). `acquire_dashboard_voice_session` cancels idle timers, refreshes stale rooms via `_refresh_dashboard_voice_room` (skips destructive delete+recreate when `room_has_active_agent` detects a live agent worker — preserves in-memory LLM conversation context across browser refreshes; otherwise recreates LiveKit room with fresh system prompt/context), creates new sessions on date change. Bootstrap sessions use `bootstrap: True` metadata (no `firstMessage`) only when the chat transcript is empty. `_expire_dashboard_voice_session` cleans up the room but preserves the session for potential reuse. `create_setup_app(db)` creates a standalone aiohttp app with dashboard routes for the setup wizard temporary server. Module-level state (`_setup_db`, `_setup_server`) coordinates between prepare completion and setup command. Settings link in gear menu dropdown points to `/dashboard/settings`.
- All lifecycle, status, and resource CLI commands emit structured JSON via `_emit_json()`. `run_status()` and `run_status_all()` return dicts (no click.echo). Resource commands (`people`, `calls`, `actions`, `facts`, `calendar`, `identity`, `soul`, `journal`, `faq`, `config`, `dashboard`) open the DB directly, query, serialize via `_serialize_item()` (dataclass → dict), and close. Config commands use dotted-path notation to get/set values across `agent.json`/`providers.json`/`intelligence.json`.
- Event emission: `config.py` provides a sync event bus (`register_event_listener`/`emit_event`). Listener registration is idempotent (deduplicates by identity). Activity events (`call_started`, `call_answered`, `call_ended`, `call_unanswered`, `facts_extracted`, `actions_extracted`, `skill_executed`) are emitted from `calls.py`, `memory.py`, and `skills.py`. `web.py` registers `_broadcast_sync` as a listener during `register_dashboard_routes()`, routing activity events to SSE clients.
- Service worker (`sw.js`, cache `mh-v2`) provides minimal PWA installability — precaches the shell (`/dashboard/page/home`) and static assets on install, falls back to cache on network failure.
- Actions support optional time slots (`start_at`/`end_at` on `Action` dataclass) and hub sync tracking (`hub_event_id`, `hub_sync_status`, `hub_sync_attempts`). When set, the action represents a time-bound event. `write-action` skill accepts `start_at`/`end_at` ISO 8601 params and pushes to the hub calendar when configured. `get_due_actions` uses `COALESCE(due_at, start_at)` so time-slot actions are scheduled by their start time when no explicit `due_at` is set. Hub write-back: skill handlers decide whether to set `hub_sync_status="pending"` (not every action with `start_at` is user-facing), `insert_action`/`update_action_status`/`update_action_time_slot` persist the flag atomically, and the scheduler retry sweep (`maybe_retry_hub_sync`) handles failures with 3-attempt exhaustion.

## Testing

- Runner: `pytest` + `pytest-asyncio`
- Command: `bash scripts/test-python.sh` or `.venv/bin/python -m pytest`
- Benchmarks: `bash scripts/bench.sh` — uses `pytest-benchmark`, excluded from default test runs via `@pytest.mark.bench` marker
- DB: real in-memory SQLite with `sqlite3` + `sqlite-vec`
- LLM: mocked at the module boundary with `unittest.mock.patch`
