# mystic/ — Python Package

## Purpose

Canonical application package for Mystic-Horizon. Single language, single process, no Node.js bridge. All modules are flat — one `.py` file per domain, no sub-packages (25 modules).

## Conventions

- Python >= 3.11
- `.venv/bin/python` is the default interpreter
- Shared on-disk formats stay stable across the cutover
- `skills/` at the repo root contains the SKILL definitions and Python handlers used by this package
- `livekit.py` owns binary discovery, installation, checksum validation, and version gating; callers should use its helpers instead of hard-coding shared binary paths. Also provides `create_named_room()`, `dispatch_agent_to_named_room()`, `delete_room()`, `generate_token()`, `parse_transcript_entries()`, and `verify_dispatch_assignment()` (polls dispatch status to detect lost dispatches).
- `cli.py` owns translation of actionable setup/runtime failures into user-facing `click.ClickException` messages. Turn detector asset checks verify concrete HuggingFace tokenizer/model files with `hf_hub_download(local_files_only=True)` rather than importing `AutoTokenizer`. Init does not run bootstrap — the dashboard home page detects missing identity/soul and starts the bootstrap conversation. Init shows download progress for model files. `seed_prompt_files` copies FAQ seeds from `FAQ_SEEDS_DIR` (repo `faq/` directory) instead of generating a hardcoded example — only copies files that don't already exist in the agent's `APP_HOME/faq/`. `run_setup` downloads the LiveKit binary, then starts a temporary setup web server (`create_setup_app`). The prepare flow downloads dependencies only (no in-process runtime). After completion, the setup server is closed to free the port, then a background daemon is spawned. If a daemon is already running, setup reuses it (skips the temporary server and daemon start). `run_setup` returns a result dict without emitting JSON directly — callers handle output. `_open_browser` uses `xdg-open`/`open` subprocess instead of `webbrowser.open`. `run_serve` preflight is advisory (logs warnings, does not block server startup). `_enter_daemon_mode` extracted from `run_serve` for shared daemon lifecycle logic. `run_start` auto-kills stale daemon processes before cleanup (`SIGTERM` with 2s wait). `ensure_dependencies` accepts an `on_step` callback for reporting download stages, an `on_detail` callback for granular progress strings (message + replace_last flag), and a `quiet: bool` parameter to suppress terminal output during web-driven prepare. Detail callbacks fire throughout each dependency stage (e.g., "Installing moonshine-voice package...", "Downloading Moonshine model (small)...", "Moonshine Voice ready"). New `run_dev` starts a foreground development server via `start_dev()` — prints readiness diagnostics (LLM, STT, TTS), supports `--skip-voice` for text-only mode, stops on `Ctrl+C`. `extract_sibling_keys` also extracts SMTP config fields, Twilio `phoneNumber`/`phoneNumberSid`. `run_connect_twilio` offers to reuse imported phone numbers. `run_connect_smtp` pre-populates defaults from sibling keys. `_prompt_secret` silently reuses imported values instead of prompting. `run_setup` wraps `open_database` and `initialize_schema` with `silence_stdout()` to suppress SQLite schema output during the setup flow. `_default_setup_selections` uses `openai/gpt-5.5` for realtime/backend and Olivia for the initial setup voice.
- `cli.py` daemon architecture: `run_start()` spawns `_serve` as a detached subprocess with stderr redirected to `APP_HOME/logs/mystic-horizon.log`, polls `probe_daemon()` until healthy, returns JSON status. On startup failure, the error includes recent log output via `_tail_log()`. `run_serve()` (hidden `_serve` command) starts `start_full()` and delegates to `_enter_daemon_mode(rt)` for the Unix socket control server. `run_stop()` sends `{"cmd": "shutdown"}` via socket, then waits for both the control socket AND the process to exit (ports fully released before returning). `run_health()` probes daemon, gathers DB stats, and uses `ensure_phone_line_ready(repair=False)` to report `twilio`, `tailscale`, `funnel`, and aggregate `phone` subsystem state plus a top-level `phone` detail block. All lifecycle and status commands emit structured JSON via `_emit_json()`. `run_status()` and `run_status_all()` return dicts (no click.echo). Port allocation uses `_port_in_use()` to probe actual port availability in addition to the known-agents set. `allocate_port` accepts a `stride` parameter — checks that all ports in `range(port, port + stride)` are free. `discover_used_ports` reserves 3 ports per LiveKit instance (HTTP + RTC TCP + RTC UDP). LiveKit port allocation uses `stride=3`.
- `cli.py` resource commands (`people`, `calls`, `actions`, `facts`, `calendar`, `identity`, `soul`, `journal`, `faq`, `config`, `dashboard`) all follow the same pattern: open DB, query, serialize via `_serialize_item()`, emit JSON, close DB. Config commands (`config get/set/show`) resolve keys across `agent.json`/`providers.json`/`intelligence.json` with dotted-path notation.
- `config.py` exports `SetupStatus` dataclass and `get_setup_status()` for checking identity, soul, Tailscale, and Twilio readiness
- `config.py` exports `TwilioDraftConfig` and persists it under `providers.json["twilioDraft"]` for Account SID/Auth Token saved before a number is attached. Full `twilio` config is only written when a phone number is available; settings and Twilio skills promote draft credentials to full config.
- `config.py` exports `TtsConfig = PocketTtsConfig | InworldTtsConfig | UnconfiguredTtsConfig` union. `_parse_tts_config` dispatches on `provider` field; returns `UnconfiguredTtsConfig` when provider is empty or missing. `InworldTtsConfig` stores `apiKey` and optional `model`.
- `config.py` exports `SttConfig = MoonshineSttConfig | DeepgramSttConfig | UnconfiguredSttConfig` union. `_parse_stt_config` dispatches on `provider` field; returns `UnconfiguredSttConfig` when provider is empty or missing. `DeepgramSttConfig` stores `apiKey` and optional `model`.
- `config.py` exports `DashboardConfig` (token field). `ensure_dashboard_token()` generates and persists a token if absent. Dashboard file CRUD: `list_dashboard_files()` enumerates `APP_HOME/dashboard/` (excludes `.history/`), `read_dashboard_file(name)` reads by relative path, `write_dashboard_file(name, content, trigger, note)` writes with automatic history snapshots on overwrite (timestamped copies with frontmatter in `dashboard/.history/`). `get_daemon_socket_path()` returns the Unix socket path for daemon IPC.
- `web.py` owns the dashboard HTTP surface. Session auth via `SESSION_COOKIE` HMAC'd from dashboard token. `register_dashboard_routes(app, db)` adds `/dashboard/*`, `/static/*`, and allowlisted `/soundfx/*` routes and registers `_broadcast_sync` as an `emit_event` listener so activity events from calls/memory/skills are pushed to SSE clients; `on_shutdown` wakes SSE queues with a `None` sentinel so streams exit cleanly. All chat goes through the LiveKit data channel — server-side chat endpoints are removed. `seed_dashboard_defaults()` copies default pages from `_assets/dashboard/defaults/` to the agent's dashboard dir; uses mtime comparison so updated defaults overwrite stale copies. `broadcast(event, data)` pushes SSE events to connected clients; `_write_sse(response, payload)` handles disconnect/runtime errors gracefully. Dashboard live voice uses `POST /dashboard/api/voice/token`, `POST /dashboard/api/voice/disconnect`, and `/dashboard/api/voice/history`; token/history payloads now include chat `history` and separate `hudHistory` from the live call transcript so the chat feed and HUD can replay the right entries independently. `acquire_dashboard_voice_session` manages session lifecycle and `_create_dashboard_room_with_agent_dispatch` uses single-shot room creation with advisory dispatch verification. Bootstrap sessions use `bootstrap: True` metadata (no `firstMessage`) only when the chat transcript is empty and pin `session_modality="text"`. `create_setup_app(db)` creates a standalone aiohttp app for setup. `_run_prepare_dependencies` downloads dependencies only and broadcasts granular prepare events. Setup page imports missing API keys and Twilio credentials from all sibling agents until it finds Twilio keys; Twilio credentials are saved as `twilioDraft` until a phone number is supplied. Settings page includes STT/TTS provider selection, Pocket voice selection, Twilio draft/full credential editing, mobile Tailscale access, a copy button for the dashboard URL, a Tailscale install hint, and a Run Setup callout that disables while the form is dirty. `_update_twilio_settings(form)` preserves existing/draft tokens when the password field is blank, writes `twilioDraft` when only credentials are present, promotes to `twilio` when a phone number is added, and clears both when credentials are removed. Settings update helpers use `_serialize_config()` instead of `asdict()` to preserve proper serialization. Relationship knowledge graph API and htmx partial rendering behavior are unchanged.
- Imports are always `from mystic.<module> import <name>` — no sub-package paths
- `AgentOwnerConfig.phone` is optional — guard clauses throughout allow fully local operation without a phone number
- Tool schemas and `execute_tool()` live in `skills.py`; each skill exposes its own tool schema via `build_skill_tool_schema(skill)` with name, description (including gotchas), modality filter, and per-skill parameters from SKILL.md frontmatter. `build_tools_for_context(registry, audience, modality)` filters by invoke permissions and modality. `voice.py` wraps skill schemas as LiveKit `@function_tool` decorators via `_make_skill_voice_tool` (raw-arguments pattern with tool event emission — `tool_started`/`tool_completed` with timing); owner dashboard sessions intentionally expose both text and voice skill modalities so text-only setup skills such as `read-twilio-numbers` are available in the shared chat/voice room. `worker.py` owns the agent entrypoint that wires them up.
- `embed_chunks` and `embed_query` live in `embedding.py` and are re-exported via `memory.py` so existing imports keep working; callers never reference ONNX specifics. Models must be pre-downloaded via `init` — inference raises if files are missing (no lazy download at query time).
- `calls.py` owns call-control primitives: `update_live_call()` mutates a live Twilio call via REST, `generate_dial_twiml()` builds `<Dial>` verbs, `reconnect_call_to_stream()` rebuilds stream TwiML after transfer/hold. Transfer target SIDs are tracked in-memory (`set_transfer_target_sid`/`clear_transfer_target_sid`) and cleaned up on call end.
- `server.py` exposes `/webhook/twilio/dial-action` for Dial verb completion (transfer result handling, stream reconnection). Status webhook handles transfer target call failures (no-answer, busy, failed, canceled).
- `audio.py` provides DTMF tone generation (`DTMF_FREQUENCIES`, `generate_dtmf_tone`) for in-call touch-tone injection.
- `config.py` caches the tunnel URL at module level (`set_tunnel_url`/`get_tunnel_url`) so call-control skills can build callback URLs without passing tunnel state through the skill context.
- `config.py` provides a sync event bus: `register_event_listener(fn)` adds a listener (idempotent — deduplicates by identity), `emit_event(event, data)` broadcasts to all listeners. Used by `calls.py`, `memory.py`, `skills.py` to emit activity events, and by `web.py` to route them to SSE clients.
- `audio_source` (LiveKit audio output handle) is threaded from `worker.py` → `voice.py` → `skills.py` → skill handlers for skills that inject audio into live calls (DTMF, hold music).
- `http.py` owns HTTP transport and low-level Tailscale lifecycle/status helpers. `phone.py` owns the higher-level Twilio/Tailscale readiness contract and calls `calls.update_phone_webhook()` when repair is allowed.
- `ink.py` owns all terminal rendering — ANSI colors, formatting utilities (`format_duration`, `format_phone`, `status_icon`, `heading`, `section`, `error_msg`), and `box()` for bordered output. Pure functions only (no I/O). `cli.py` imports from `ink.py` instead of defining its own formatting.
- `voice.py` exports `MysticAgent`, a `livekit.agents.Agent` subclass installed as the default `agent_cls` in `create_pipeline`. Before each user turn it removes any prior `mh-time-*` marker messages and inserts a fresh system message with the agent-configured timezone's wall-clock stamp (e.g., `Current time: Thursday, April 16, 2026 03:42 PM America/Los_Angeles`). The LLM sees exactly one time stamp per turn, always current — this replaces the stale-time problems of injecting time via static system prompt context.
- `llm.py` adds `DEFAULT_LLM_MAX_TOKENS = 4096` to non-LiveKit OpenRouter/custom requests (`invoke_agent`, `stream_llm_tokens`, and `stream_llm_with_tools`). It routes `task == "search"` (i.e., `read-search`) through a dedicated OpenRouter backend returned by `_get_openrouter_search_backend()` — the configured realtime/backend LLM is ignored for this task, and the model is always `OPENROUTER_SEARCH_MODEL = "perplexity/sonar-pro"`. Raises `ValueError` if the OpenRouter API key is missing. Search requests still carry OpenRouter referrer/title headers.
- `voice.py` `create_stt()` dispatches on `SttConfig` type: `UnconfiguredSttConfig` → raises `RuntimeError`, `DeepgramSttConfig` → lazy `importlib.import_module("livekit.plugins.deepgram")`, `MoonshineSttConfig` → native Moonshine Voice. Deepgram default model is `nova-3`. `create_tts()` similarly raises `RuntimeError` for `UnconfiguredTtsConfig`. `create_llm()` passes `DEFAULT_LLM_MAX_COMPLETION_TOKENS = 4096` into the LiveKit OpenAI-compatible LLM. `build_agent_tools` dynamically builds per-skill tools from the registry; by default it uses the context modality, but owner dashboard sessions intentionally merge voice + text tool sets so setup/dashboard tools are available in the shared room. `_make_skill_voice_tool` wraps each skill schema as a LiveKit `@function_tool` with raw-arguments pattern and tool event emission (`tool_started`/`tool_completed` with timing via `on_tool_event` callback). Tool argument summaries prefer user-facing fields including `phone_number` and `area_code`. The `chat` tool is intercepted before skill dispatch and routed through `_send_chat_tool_message`, which uses the `on_send_text` callback directly instead of invoking the skill handler. `create_pipeline` appends `_TOOL_NARRATION` to the system prompt — instructs the agent to narrate tool use so voice callers aren't left in silence.
- `worker.py` logs per-item metrics (transcription_delay, end_of_turn_delay from user items; llm_ttft, tts_ttfb, e2e_latency from assistant items) via `ConversationItemAddedEvent.item.metrics`. `AgentSession` configured with `turn_handling=_build_turn_handling()` — uses multilingual turn detector plugin if available, falls back to simple endpointing (`min_delay=0.2`). Plugin init failures are caught gracefully (logs warning, uses fallback). When the plugin is present, configures dynamic endpointing (0.2–1.5s), VAD interruption mode (resume false interruptions, 2s timeout, min 0.3s/1 word). Agent transcript events (`user_input_transcribed`, `user_chat_received`, `agent_chat_response`, `tool_started`, `tool_completed`, `agent_error`) published to `lk.agent.events` LiveKit data channel via `local_participant.publish_data()`. Agent speech is delivered to the browser via native LiveKit transcription text streaming (`lk.transcription`) — no `conversation_item_added` event publishing. Text and voice input share a unified pipeline — text input calls `session.interrupt()` then `session.generate_reply(user_input=text)`. No `last_input_modality` tracking — agent speech routing is handled by the LiveKit SDK's native transcription streaming. Chat transcript entries persisted to a call record via `_append_chat_entry` (uses `chatCallId` from room metadata); agent speech also persisted. Text input accepted via both `room_io.TextInputOptions` and `mh.chat` data channel (`data_received` handler — parses `clientMessageId` from JSON payload, uses `asyncio.create_task` with named tasks). Text deduplication uses `clientMessageId` (preferred) or stream ID as dedupe key via `seen_text_stream_ids` set. `user_chat_received` events include `clientMessageId` when present. `_safe_process_text_input` wraps `_process_text_input` with error handling — catches exceptions, logs warnings, publishes `agent_error` events. Tool events forwarded from `AgentToolUserData.on_tool_event` callback to `lk.agent.events` data channel. Idle session timeout (120s, reset by any data channel activity including heartbeat pings) auto-closes sessions without activity. `send_text` tool callback (`on_send_text`) publishes `agent_chat_response` events and records transcript. Pipeline creation failures publish `agent_error` events. Bootstrap sessions (`metadata.bootstrap=True` with no `firstMessage`) call `session.generate_reply()` to produce an initial conversational reply instead of speaking a hardcoded message. Worker port set to `0` (OS-assigned) to avoid conflicts. Worker drain timeout 3s with `aclose` timeout 3s and task wait timeout 2s. Voice control: `mh.voice_control` data channel topic accepts `{"action": "start"|"stop"}` packets — `_handle_voice_control` toggles `voice_audio_enabled` and calls `_set_session_audio_enabled` (inspects+awaits sync or async `set_audio_enabled` on session input/output endpoints). Dashboard inbound owner sessions (`direction=inbound`, `audience=owner`) start with audio disabled on both session input and output; non-dashboard calls keep audio enabled. Agent speech modality is tracked via `voice_audio_enabled` — when disabled, `collector.add_agent_speech` records `modality="text"` and agent speech publishes `agent_chat_response` events + appends to chat feed instead of voice delivery.

- `calendar.py` owns ICS feed sync (`sync_subscription`, `maybe_sync`), availability checks (`check_availability`), open slot computation (`find_open_slots`), reminder notifications (`check_reminders`), schedule formatting for prompts (`format_current_schedule`, `format_upcoming_schedule`), hub calendar write-back (`create_hub_event`, `update_hub_event`, `delete_hub_event`), OAuth2 flow (`run_oauth_flow`, `ensure_valid_token` with staleness guard), and scheduler retry sweep (`maybe_retry_hub_sync`). Hub write-back supports Google Calendar API, Microsoft Graph API, and CalDAV (PUT/DELETE). Provider dispatch uses plain dicts of callables (`_HUB_CREATORS`, `_HUB_UPDATERS`, `_HUB_DELETERS`). `_hub_call_with_retry` handles 401 errors by force-refreshing the token and retrying once. `maybe_retry_hub_sync` processes up to 5 pending actions per scheduler tick with status-aware dispatch (cancelled → delete, active with `hub_event_id` → update, new → create), increments attempts on failure, and marks `"failed"` after `_HUB_MAX_RETRIES` (3). Populates `current_schedule` and `upcoming_schedule` via `calendar.py` formatters, `verbatim_recent_context` (unfinalized verbatim transcripts via `get_unfinalized_interactions` — includes current day plus prior days with unfinalized summaries, with time/channel/modality labels), `recent_days_summary` (up to 7 finalized day summaries from up to 30-day lookback via `is_day_summary_finalized`), `channel_label`, `modality`, `direction` (human-readable labels via `describe_interaction`), and `phone_setup_hint` (for owner audience when Twilio is unconfigured — nudges the agent to use the setup skills directly, including `read-twilio-numbers`, instead of only sending the owner to Settings). - `actions.py` scheduler tick calls `maybe_sync(db)`, `check_reminders(db)`, and `maybe_retry_hub_sync(db)` before processing due actions — local imports to avoid circular dependency. All are no-ops when calendar config is absent.
